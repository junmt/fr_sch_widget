## 1. 背景と目的

### 1.1 背景

- 予定を忘れていて、気づいたら開始時刻になっていることが多い。
- 他の人に予定を急に入れられることがあり、朝に確認した内容が古くなる。

### 1.2 目的

1. **いつも見える場所に今日の予定を出す**：デスクトップ上に常駐するウィジェットで表示する。
2. **最新の状態を保つ**：数分おきに F-RevoCRM からデータを取り直して表示を更新する。
3. **気づかせる**：新しく入った予定や開始が近い予定を目立たせて通知する。

### 1.3 スコープ

| 区分 | 内容 |
|---|---|
| 対象 | 自分（ログインユーザー）が担当者になっている、今日の活動（Events：会議・電話などの予定） |
| 対象外（初版） | 予定の作成・編集・削除（表示専用）、ToDo、他ユーザーの予定、Windows 以外のOS |
| 将来の検討 | ToDo の表示、招待された予定（参加者として登録された予定）の表示 |

### 1.4 対応する F-RevoCRM のバージョン

- **古いバージョンでも動くこと**を前提にする。そのため、昔からある標準の Webservice API（`webservice.php` の `getchallenge` / `login` / `query` / `logout`）だけを使う。
- 新しいバージョンにだけあるモバイルAPI（`mobileauth` / `get_schedules` など）や、CRM 本体の内部 API（`index.php?api=...`）は使わない。
  - モバイルAPIは、新しいバージョンでも DB に登録されていないと使えない。内部 API はブラウザでログインしたときの Cookie と CSRF トークンが前提になっている。どちらも外部のアプリから使うには向かない。
- CRM 側には何も手を加えない（プログラムの追加や設定の変更はいらない）。

## 2. 用語

| 用語 | 意味 |
|---|---|
| 活動 / 予定 | F-RevoCRM の Events モジュールのレコード（活動種別: Call / Meeting など） |
| Webservice API | F-RevoCRM（vtiger 互換）の `webservice.php` による標準のAPI |
| アクセスキー | F-RevoCRM の「マイ設定」画面に表示される、API 用のキー。パスワードとは別のもの |
| セッション | `login` で受け取る `sessionName`。以降の API 呼び出しに付けて送る |
| VTQL | Webservice API の `query` で使う、SQL に似た問い合わせ言語 |
| ポーリング | 決まった間隔でサーバーへデータを取りにいくこと |

## 3. システム構成

```
┌──────────────────── Windows PC ────────────────────┐          ┌──────── F-RevoCRM ────────┐
│  ウィジェット (Tauri 2 アプリ)                       │          │                            │
│                                                     │  HTTPS   │  /webservice.php           │
│  ┌ Rust (バックエンド) ─────────────────────┐       │ ───────▶ │   getchallenge             │
│  │ ・ポーリング (既定 3分間隔)              │       │ ◀─────── │   login                    │
│  │ ・API通信 / セッション管理               │       │   JSON   │   query (Events)           │
│  │ ・UTC → ローカル時刻の変換               │       │          │   logout                   │
│  │ ・資格情報の保存 (資格情報マネージャー)  │       │          └────────────────────────────┘
│  │ ・トレイ / 通知 / 自動起動               │       │
│  └──────────────┬───────────────────────────┘       │
│        イベント │ (予定一覧・状態)                   │
│  ┌ WebView2 (画面) ─────────────────────────┐       │
│  │ ・HTML / CSS / TypeScript                │       │
│  │ ・表示、差分の強調、毎分の再計算         │       │
│  └──────────────────────────────────────────┘       │
└─────────────────────────────────────────────────────┘
```

### 3.1 技術構成

| 項目 | 採用 | 備考 |
|---|---|---|
| フレームワーク | **Tauri 2** | Windows 標準の WebView2 を使うため、ブラウザを同梱せずに軽く作れる |
| 画面 | HTML / CSS / TypeScript（Vite） | 画面は1つだけなので、UI フレームワークは使わないか軽量なもの（Preact / Svelte など）にする |
| バックエンド | Rust | API通信、ポーリング、セッション管理、時刻の変換、差分の判定、通知を担当する |
| HTTP 通信 | `reqwest` | 画面（WebView）からは CRM と直接通信しない。CORS や CSP を気にしなくてよくなり、アクセスキーやセッションも画面に渡さずにすむ |
| 日時 | `chrono` | UTC からローカル時刻への変換 |
| ハッシュ | `md5` クレート | `login` のときにアクセスキーをハッシュするのに使う |
| 資格情報の保存 | `keyring` クレート（Windows 資格情報マネージャー） | アクセスキーを平文でファイルに置かない |
| 設定の保存 | `%APPDATA%\fr-sch-widget\config.json` | `tauri-plugin-store` でも可 |
| 公式プラグイン | `tray-icon`（コア機能）、`tauri-plugin-notification`、`tauri-plugin-autostart`、`tauri-plugin-window-state`、`tauri-plugin-single-instance`、`tauri-plugin-opener`、`tauri-plugin-log` | |
| 配布 | NSIS インストーラー（WebView2 がない環境向けにブートストラッパーを入れる） | |
| 開発環境 | Rust（rustup, MSVC ツールチェーン）、Visual Studio Build Tools（C++）、Node.js | |

#### 役割の分担

| 処理 | 担当 |
|---|---|
| ログイン・予定の取得・時刻の変換 | Rust |
| 前回との差分（新規・変更・削除）の判定、通知を出す | Rust（画面を隠していても動かすため） |
| 開始前のリマインド通知 | Rust（毎分チェック） |
| 一覧の描画、状態（進行中・直前など）の表示、残り時間の再計算 | 画面（TypeScript） |
| Rust → 画面 | `state-changed`（予定一覧・同期の状態・表示の設定をまとめたもの）と `focus-item`（通知をクリックしたときに強調する予定の id）のイベントで送る |
| 画面 → Rust | `get_state`、`refresh_now`、`open_record`、`dismiss_badge`、`open_settings`、`get_settings` / `save_settings`、`test_connection` のコマンドを呼ぶ |

## 4. 機能要件

### F-01 今日の予定表示

- 今日（PC のローカル日付、00:00〜23:59）にかかる予定をすべて表示する。
  - 前日から続く予定や翌日まで続く予定（日をまたぐ予定）も含める。
- 並び順：終日予定を一番上にまとめ、その下に開始時刻の早い順に並べる。
- 1件ごとに表示する項目：

| 項目 | 取得元フィールド | 備考 |
|---|---|---|
| 開始〜終了時刻 | `date_start` `time_start` / `due_date` `time_end` | UTC からローカル時刻に直して表示する。終日なら「終日」と表示 |
| 件名 | `subject` | 長い場合は末尾を「…」で省略し、マウスを乗せると全文を表示 |
| 活動種別 | `activitytype` | アイコンまたはラベルで表示（Call / Meeting など） |
| 場所 | `location` | 空なら表示しない |
| ステータス | `eventstatus` | Held（完了）は打ち消し線、Not Held（中止）は薄く表示 |

- 予定ごとの状態に応じて見た目を変える：

| 状態 | 条件 | 表示 |
|---|---|---|
| 終了 | 終了時刻 < 現在 | 文字を薄く（グレー） |
| 進行中 | 開始 ≦ 現在 < 終了 | 背景を強調色にし「進行中」バッジを付ける |
| 直前 | 現在 < 開始 ≦ 現在 + 直前とみなす時間（既定15分） | 枠をオレンジにし「あと◯分」を表示 |
| 次の予定 | 未開始の予定のうち一番早いもの | 「次」バッジを付ける |
| 新着 | 前回の取得になかった予定 | 「NEW」バッジを付ける（クリックするか30分たつと消える） |
| 変更 | 前回から時刻が変わった予定 | 「変更」バッジを付ける（消えるタイミングは新着と同じ） |

- ヘッダー：今日の日付（例：`10/27(火)`）、件数、次の予定までの残り時間。
- フッター：最終更新時刻（例：`更新 13:42`）、手動更新ボタン。
- 予定が0件のときは「今日の予定はありません」と表示する。
- 残り時間や状態の表示は、API の取得とは別に **毎分（00秒ちょうど）** 再計算して更新する。

### F-02 定期取得（ポーリング）

- 既定では **3分おき** にデータを取り直す。設定で 1〜30分の範囲で変更できる。
- 次のタイミングでもすぐに取り直す：
  - アプリ起動時
  - 手動更新ボタン、またはトレイメニューの「今すぐ更新」を押したとき
  - PC がスリープから復帰したとき
  - 日付が変わったとき（0:00 になったら翌日の予定に切り替える）
- スリープ復帰や日付の変更は、「タイマーの前回の実行時刻と今の時刻の差が、間隔より大きく開いた」ことで判定する（OS のイベントに頼らない）。
- 取得に失敗しても、前回取得できたデータの表示を続ける（「F-08 エラー処理」を参照）。
- 同時に複数の取得を実行しない（前の取得が終わるまで次の取得は始めない）。

### F-03 変更の検知と通知

- 前回取得したデータと、予定の `id` をキーにして比べ、次の変化を見つける：

| 変化 | 判定方法 | 動作 |
|---|---|---|
| 新規 | 前回になかった `id` | 「NEW」バッジ ＋ Windows 通知「新しい予定: 14:00 ◯◯打合せ」 |
| 時刻の変更 | 同じ `id` で開始・終了の日時が違う | 「変更」バッジ ＋ Windows 通知「予定の時刻が変わりました: 14:00→15:00 ◯◯打合せ」 |
| 削除・取消 | 前回あった `id` が今回ない | 一覧から消す（通知するかは設定で選ぶ、既定はしない） |

- 件名や場所だけが変わったときは、表示を更新するだけで通知しない。
- 次のときは通知しない（すべてが「新規」扱いになってしまうため）：
  - アプリを起動して最初に取得したとき
  - 日付が変わって最初に取得したとき
  - エラーから回復して最初に取得したとき（バッジだけ付ける）

### F-04 開始前のリマインド

- 予定の開始 N 分前（既定 **10分前**、設定で変更可、複数指定可 例：`10,1`）に Windows 通知を出す。
- 通知をクリックすると、ウィジェットを前面に出し、その予定を強調する。
- 同じ予定・同じタイミングの通知は1回だけにする（通知済みの記録を当日分だけ持つ）。
- 時刻が変わった予定は、新しい時刻を基準にもう一度リマインドする。
- 終日予定と、ステータスが Held / Not Held の予定はリマインドしない。
- PC のスリープ中に通知の時刻が過ぎた場合、開始前であれば復帰した時点ですぐに通知する。開始後であれば通知しない。

### F-05 予定の詳細を開く

- 予定をクリックすると、既定のブラウザで F-RevoCRM のその予定の詳細画面を開く。
  - URL：`{CRMのURL}/index.php?module=Calendar&view=Detail&record={レコードID}`
  - レコードID は `id`（例 `18x1234`）の `x` より後ろの数字。

### F-06 ウィンドウ（ウィジェット）

| 項目 | 仕様 |
|---|---|
| 見た目 | 枠なし（`decorations: false`）、角丸、背景は半透明（`transparent: true`。不透明度は設定で変更可） |
| 大きさ | 既定 幅320px × 高さ420px。端をドラッグして変更できる。予定が多いときは中をスクロールする |
| 位置 | ヘッダーをドラッグして移動できる（`data-tauri-drag-region`）。位置と大きさは保存し、次回起動時に元に戻す。保存した位置のモニターが外されているときは、メインモニターの右上に表示する |
| 重なり順 | 「常に最前面に表示」を設定で ON/OFF（既定 ON、`alwaysOnTop`） |
| タスクバー | タスクバーには表示せず（`skipTaskbar: true`）、タスクトレイにアイコンを置く |
| 閉じる | ウィンドウを閉じても終了せず、隠すだけにする。終了はトレイメニューから行う |
| 多重起動 | 2つ目を起動しようとしたら、すでに動いているウィジェットを前面に出す |
| 折りたたみ | ヘッダーをダブルクリックすると「次の予定1件だけ」の小さな表示に切り替わる |
| 右クリック | WebView の標準のメニュー（戻る・印刷など）は出さず、このアプリのメニューを出す：予定の上なら「CRM で開く」、どこでも「今すぐ更新」「折りたたむ / 広げる」「常に最前面に表示」「設定...」「アップデートを確認」「ウィジェットを隠す」「終了」。設定画面は入力欄でだけ標準のメニュー（貼り付けなど）を出す |
| 時刻の見せ方 | 開始時刻を一覧の左に大きく太く表示し（進行中は青、直前はオレンジ）、終了時刻はその下に小さく「〜12:00」と出す。翌日に終わるときは「〜翌01:00」、2日以上あとなら「〜10/29 18:00」。前日から続く予定は時刻の上に日付を付ける。ヘッダーの「次は 18:00 件名 ・ あと25分」と折りたたみ表示でも時刻を大きくする |
| DPI | 高DPI（125%・150% など）やモニターごとの拡大率の違いに対応する |
| テーマ | ライト / ダーク / Windows の設定に合わせる |

### F-07 タスクトレイ

- 右クリックメニュー：
  - 今すぐ更新
  - ウィジェットを表示 / 隠す
  - 常に最前面に表示（チェックで切り替え）
  - 設定
  - 終了
- 左クリックでウィジェットの表示 / 非表示を切り替える。
- トレイアイコンにマウスを乗せると「次: 14:00 ◯◯打合せ（あと25分）」と表示する。
- エラーが起きているときは、アイコンを警告マーク付きのものに変える。

### F-08 エラー処理

| 状況 | 判定 | 動作 |
|---|---|---|
| ネットワークにつながらない・タイムアウト（15秒） | 通信エラー | 前回のデータを表示したまま、フッターに「⚠ 接続できません（最終更新 13:42）」と表示し、次の間隔で再試行する |
| セッション切れ | `INVALID_SESSIONID` / `SESSION_EXPIRED` / `SESSION_LEFT_IDLE` / `AUTHENTICATION_REQUIRED` | `getchallenge` → `login` をやり直して、もう一度取得する（1回だけ） |
| 認証の制限（F-RevoCRM の不具合。5.2 を参照） | 新しく取ったトークンでの `login` が `INVALID_USER_CREDENTIALS` | 「CRM の認証の制限（5分に1回）のため、HH:MM に再試行します」と表示し、トークンが切れる時刻（5分後 + 10秒）に自動で再試行する。間隔を延ばす対象にはしない |
| ユーザー名・アクセスキーの誤り | 制限が解けたあとも `login` が失敗する、または使い回したトークンで失敗する。`AUTHENTICATION_FAILURE` / `ACCESSKEY_UNDEFINED` | ポーリングを止め、「ログインできません：ユーザー名とアクセスキーを確認してください」と表示する。自動では再試行しない |
| 権限がない | `ACCESS_DENIED` / `PERMISSION_DENIED` | ポーリングを止め、「予定を見る権限がありません」と表示する |
| 予期しない応答 | JSON でない（HTML のエラーページやログイン画面が返ってきたなど） | 通信エラーと同じ扱いにし、レスポンスの先頭部分をログに残す |
| 続けて失敗する | 通信エラーが続く | 再試行の間隔を延ばす（設定した間隔 → 2倍 → 4倍、最大15分）。成功したら元の間隔に戻す |
| 最終更新から30分以上たっている | | ヘッダーを警告色にして、データが古いことがひと目でわかるようにする |

- 前回取得したデータは端末内（`%APPDATA%\fr-sch-widget\cache.json`）に保存し、アプリを起動した直後やオフラインのときにも表示する。使うのはその日の分で、**同じ条件で作ったものだけ**（キャッシュの形式のバージョン・CRM の URL・ユーザー名・サーバーのタイムゾーンが同じもの）。条件が違うキャッシュ（古い版が保存したものを含む）は使わない。
- 一度も取得できていないときは、一覧に「まだ予定を取得していません」と表示する（「今日の予定はありません」と区別する）。

### F-09 接続設定とその他の設定

#### 接続設定

- 初めて起動したとき、接続設定が空なら設定画面を自動で開く。
- 入力項目：CRM の URL、ユーザー名、アクセスキー。
  - アクセスキーの確認方法を画面に書いておく：「F-RevoCRM の右上のユーザーメニュー →『マイ設定』→『ユーザーの詳細』にある『アクセスキー』」。
  - アクセスキーで `login` するので、ブラウザでのログインに MFA（2段階認証）を設定していても関係なく使える。
- アクセスキーは資格情報マネージャーに保存する。`sessionName` はメモリ上だけに持つ。

#### 設定項目

| 設定項目 | 既定値 | 備考 |
|---|---|---|
| CRM の URL | （必須） | 例 `https://crm.example.co.jp/frevocrm`。末尾の `/` や `/index.php` は取り除いて保存する。HTTPS 以外のときは警告を出す |
| CRM サーバーのタイムゾーン | PC と同じ | 「PC と同じ（日本時間など。F-RevoCRM の既定）」か「UTC（本家 vtiger の既定）」。5.3 を参照 |
| ユーザー名 | （必須） | |
| アクセスキー | （必須） | 入力欄は伏せ字にする |
| 更新間隔（分） | 3 | 1〜30 |
| 開始前リマインド（分） | 10 | カンマ区切りで複数指定可。空なら通知しない |
| 直前とみなす時間（分） | 15 | 「直前」表示の基準 |
| 新着・変更の通知 | ON | |
| 削除の通知 | OFF | |
| 表示する活動種別 | すべて | Call / Meeting などを選んで絞り込める |
| 中止（Not Held）の予定を表示 | ON | |
| 完了（Held）の予定を表示 | ON | |
| 常に最前面に表示 | ON | |
| 不透明度 | 90% | 50〜100% |
| テーマ | Windows に合わせる | |
| Windows 起動時に自動で起動 | ON | |
| 新しいバージョンを自動で確認する | ON | F-11 |

- 「接続テスト」ボタン：ログインと今日の予定の取得を試して、結果（成功・件数 / エラー内容）を表示する。
- 保存したらすぐに反映する（アプリの再起動はいらない）。

### F-10 自動起動

- Windows にサインインしたときに自動で起動する（設定で ON/OFF。`tauri-plugin-autostart`）。
- 起動するとトレイに常駐し、ウィジェットを表示する。

### F-11 自動アップデート

- GitHub のリリース（`https://github.com/junmt/fr_sch_widget/releases/latest/download/latest.json`）を見て、新しいバージョンがあるかを確認する（`tauri-plugin-updater`）。
- 確認するタイミング：
  - 起動してから30秒後（起動直後の予定の取得と重ならないようにする）
  - その後は6時間おき（前回の確認から6時間以上たっていたら確認する。PC の時計が戻った場合も確認する）
  - トレイメニューの「アップデートを確認」を押したとき（結果を「最新です」「確認できませんでした」も含めて通知する）
  - 設定で「新しいバージョンを自動で確認する」を OFF にしたときは、手動の確認だけにする
- 新しいバージョンがあったら：
  - Windows 通知で知らせる（同じバージョンの通知は1回だけ。手動で確認したときは毎回）
  - ウィジェットのフッターに「⬆ v◯ に更新」ボタンを出す
  - トレイメニューの「v◯ に更新して再起動」を押せるようにする
- 更新はユーザーが押したときだけ行う（勝手に再起動しない）。押すと確認のダイアログを出し、OK なら CRM からログアウトしてから、更新をダウンロードしてインストールする。インストーラーは画面を最小限にした表示（passive）で動き、終わるとアプリが起動し直す。
- 更新ファイルには署名を付け、アプリに埋め込んだ公開鍵で確かめる。署名が合わない更新はインストールしない。
  - 秘密鍵とパスワードは GitHub のシークレット（`TAURI_SIGNING_PRIVATE_KEY`、`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`）に置き、リリースのワークフローだけで使う。
  - 秘密鍵をなくすと、すでに配ったアプリに更新を届けられなくなるので、安全な場所に控えを残す。

## 5. データ取得の仕様（標準 Webservice API）

参考：F-RevoCRM リポジトリの `docs/specs/webservice/webservice.md`、実装は `include/Webservices/`。

### 5.1 共通

- エンドポイント：`{CRMのURL}/webservice.php`
- レスポンスは `{"success": true, "result": ...}`、または `{"success": false, "error": {"code": "...", "message": "..."}}`。
- HTTP のステータスが 200 でも `success: false` のことがあるので、必ず `success` を見て判定する。

### 5.2 ログイン

```
1. GET  {URL}/webservice.php?operation=getchallenge&username={ユーザー名}
        → result.token（チャレンジトークン）, result.serverTime, result.expireTime

2. POST {URL}/webservice.php
        Content-Type: application/x-www-form-urlencoded
        operation=login&username={ユーザー名}&accessKey={md5(token + アクセスキー)}
        → result.sessionName, result.userId（例 "19x5"）
```

- `accessKey` には、チャレンジトークンとアクセスキーをつなげた文字列の MD5（16進の小文字32桁）を入れる。
- `sessionName` と `userId` はメモリ上に持ち、取得のたびに使い回す。毎回ログインし直すことはしない。
- セッションが切れたら（F-08）、ログインし直す。

#### F-RevoCRM の認証の不具合への対策

F-RevoCRM（修正前の版）では、**前の認証から5分以内にもう一度認証すると必ず失敗する**。

- 原因：チャレンジトークンのテーブル（`vtiger_ws_userauthtoken`）は1ユーザーに有効なトークンを1つしか持てない（`userid` が UNIQUE）。有効なトークンがある間（`expireTime` までの5分間）に `getchallenge` を呼ぶと、新しいトークンの保存に失敗するのに、そのトークンを返してしまう。そのトークンでの `login` は `INVALID_USER_CREDENTIALS`（ユーザー名かアクセスキーが違う）になる。
- 起きる場面：「接続テスト」の直後の取得、アプリの再起動、セッション切れのあとのログインし直しなど。

そこで、次のように動く（`crm::AuthState`）。

1. **トークンを使い回す**：ログインに成功したトークンと有効期限（`expireTime - serverTime` をこの PC の時計に足したもの）を覚えておく。有効期限まで15秒以上あれば、`getchallenge` を呼ばずにそのトークンで `login` する。
   - ログインに成功したトークンは DB に保存されていることが確かなので、5分以内でも認証できる。
   - 覚えたトークンは `%APPDATA%\fr-sch-widget\auth.json` に保存し、アプリを起動し直しても使う（トークンだけではログインできないので秘密情報ではない）。接続テストとも共有する。
2. **使い回したトークンで `INVALID_USER_CREDENTIALS`**：DB にあるはずのトークンで失敗したので、アクセスキーが違うとすぐに判断する。`INVALID_AUTH_TOKEN`（トークンが消えていた）なら、`getchallenge` から取り直す。
3. **新しいトークンで `INVALID_USER_CREDENTIALS`**：この不具合か、アクセスキーの誤りかは区別できない。
   - 1回目は「認証の制限」とみなし、トークンが切れる時刻（5分 + 10秒後）に自動で再試行する。失敗したトークンは覚えない（DB にないため）。
   - 制限が解ける時刻を過ぎても失敗したら、アクセスキーが違うとみなす（認証エラーで止める）。
   - 制限中に手動更新や設定の保存で再試行して成功したら（不具合が直った CRM や、アクセスキーを直した場合）、制限を解く。

- アプリを終了するときは `operation=logout&sessionName={s}` を POST する（失敗しても無視してよい）。

### 5.3 予定の取得

```
GET {URL}/webservice.php?operation=query&sessionName={s}&query={VTQL（URLエンコード）}
```

VTQL：

```sql
SELECT id, subject, activitytype, date_start, time_start, due_date, time_end,
       eventstatus, location, visibility, modifiedtime
FROM Events
WHERE assigned_user_id = '{userId}'
  AND date_start <= '{明日の日付}'
  AND due_date >= '{昨日の日付}'
ORDER BY date_start
LIMIT {offset}, 100;
```

- **日時は CRM サーバーのタイムゾーンで返ってくる**。vtiger 系は、予定の日時をサーバーの PHP のタイムゾーン（`config.inc.php` の `$default_timezone`）で DB に保存し、`query` はそれを変換せずにそのまま返す（`DataTransform::sanitizeDataWithColumn` では日付を変換していない。保存するときは `DateTimeField::convertToDBTimeZone` でユーザーのタイムゾーンからサーバーのタイムゾーンに直している）。
  - F-RevoCRM の既定は `Asia/Tokyo`、本家 vtiger の既定は `UTC`。サーバーのタイムゾーンは API からは分からないので、設定の「CRM サーバーのタイムゾーン」で選ぶ（既定は「PC と同じ」）。
    - 「PC と同じ」：返ってきた値をそのまま使う。
    - 「UTC」：返ってきた値を UTC として読み、PC のローカル時刻に直す。
  - WHERE 句の日付もサーバーのタイムゾーンの日付と比べられるので、取得の条件は「開始日 ≦ 明日、かつ終了日 ≧ 昨日」と前後1日ずつ広めにとる（UTC のサーバーでは、日本時間の今日 00:00〜23:59 は前日 15:00〜当日 14:59 になるため）。
  - 直した時刻で「開始 < 明日 00:00、かつ 終了 > 今日 00:00」（開始と終了が同じ時刻の予定は「開始が今日の中」）にあてはまる予定だけを残す。
  - 「開始日 ≦ X、かつ終了日 ≧ Y」という重なりの条件なので、何日も続く長い予定も取りこぼさない。
- `query` は1回で最大100件しか返さない。100件返ってきたら `offset` を100ずつ増やして、100件未満になるまで続きを取る。
- 古いバージョンの VTQL では、使える構文が少ないことがある（OR やかっこが使えないなど）。そのため条件は AND だけで書き、細かい絞り込み（活動種別やステータス）は手元で行う。
  - `ORDER BY` が使えない環境のことも考えて、並べ替えも手元で行う（`ORDER BY` は付けなくてもよい）。
- 古いバージョンでは指定したフィールドがない場合がある。`SELECT` が失敗したときは `SELECT * FROM Events ...` で取り直す。
- `time_end` が空の予定は、開始から30分の予定として扱う。

### 5.4 終日予定の判定

- 古いバージョンには「終日」のフラグがない。そこで、CRM のカレンダー画面と同じ考え方で判定する：ローカル時刻に直したときに、**開始も終了も 00:00 なら終日**とみなす。
  - 例：開始 `10/27 00:00`、終了 `10/28 00:00` → 10/27 の終日予定。
  - 開始と終了が同じ日の 00:00 なら、その日1日の終日予定とする。
- 実データで確かめて、必要なら判定を直す（→ 9章 未決事項）。

### 5.5 内部のデータモデル

```ts
interface ScheduleItem {
  id: string;            // "18x1234"
  recordId: number;      // 1234
  subject: string;
  activityType: string;  // Call / Meeting / ...
  start: string;         // ローカル時刻に直したもの "2026-10-27T09:00"
  end: string;
  allDay: boolean;
  status: string;        // Planned / Held / Not Held
  location?: string;
  modifiedTime: string;  // 参考（UTC のまま）
  badge?: "new" | "changed";  // 差分の判定結果
}
```

## 7. 非機能要件

| 区分 | 要件 |
|---|---|
| 性能 | 1回の取得は通常2秒以内に終わること。常駐時のメモリは WebView2 を含めて 80MB 程度まで、ふだんの CPU 使用率はほぼ0%であること。インストーラーは 15MB 以下 |
| CRM への負荷 | 1台あたり既定で3分に1回の `query` にする（ログインはセッションが切れたときだけ）。1分未満の間隔は設定させない |
| セキュリティ | アクセスキーは Windows 資格情報マネージャーに保存し、ファイルやログには出さない。`sessionName` はメモリ上だけに持ち、画面（WebView）には渡さない。ログに URL を出すときは `sessionName` を伏せる。通信は HTTPS を前提とし、証明書エラーの無視はしない（社内の自己署名証明書を使う場合は、Windows の証明書ストアに登録して対応する）。Tauri の capabilities で、画面から呼べるコマンドを必要なものだけに絞る |
| 信頼性 | スリープからの復帰・ネットワークの切断・日付の変更があっても、手で再起動しなくても正しく動き続けること |
| ログ | `%LOCALAPPDATA%\fr-sch-widget\logs\widget.log` に出力する。1MB を超えたら新しいファイルに切り替え、古いものは7つまで残す。取得の成功・失敗、エラー内容を記録する |
| 対応環境（PC） | Windows 10 22H2 以降 / Windows 11（WebView2 ランタイムが必要。Windows 11 には標準で入っている） |
| 対応環境（CRM） | 標準の Webservice API（`webservice.php`）が使える F-RevoCRM すべて（古いバージョンを含む）。CRM 側の変更はいらない |

## 8. 受け入れ基準

1. 接続設定を入れると、今日の自分の予定が時刻順に表示され、時刻が CRM の画面と同じになっている（タイムゾーンのずれがない）。
2. CRM 上で今日の予定を追加すると、更新間隔＋1分以内にウィジェットに「NEW」付きで表示され、Windows 通知が出る。
3. CRM 上で予定の時刻を変更すると、更新間隔＋1分以内に表示が変わり、「変更」の通知が出る。
4. 予定の開始10分前に Windows 通知が出る。
5. 進行中・直前・終了の表示が、現在時刻に合わせて毎分切り替わる。
6. ネットワークを切っても前回のデータを表示し続け、つながると自動で元に戻る。
7. セッションが切れても、自動でログインし直して取得を続けられる。
8. 0:00 をまたぐと翌日の予定に切り替わる。
9. スリープから復帰するとすぐに最新のデータになる。
10. PC を再起動すると自動で起動し、前回の位置に表示される。
11. 日をまたぐ予定・何日も続く予定・終日予定・朝9時より前（UTC では前日になる）の予定が正しく表示される。
12. 今日の予定が100件を超えても、すべて表示される。
13. 常駐時のメモリが 80MB 程度に収まっている。

## 9. 未決事項・確認事項

| No | 内容 | 対応方針（案） |
|---|---|---|
| 1 | 対象にする一番古い F-RevoCRM のバージョン | 利用者に確認する。そのバージョンで VTQL の構文（`ORDER BY`、日付の比較）と `Events` のフィールド名を実際に確かめる |
| 2 | 終日予定の保存のされ方（開始・終了とも 00:00 になっているか） | 実データで確かめる |
| 3 | 参加者（招待された人）として登録された予定も表示するか | `query` では担当者でしか絞り込めないため、初版は対象外 |
| 4 | ToDo（Calendar モジュール）の期限が今日のものも表示するか | 初版は対象外。要望があれば `FROM Calendar` で別に取得して、別のセクションで表示する |
| 5 | 繰り返し予定の扱い | F-RevoCRM では繰り返し予定は1件ずつのレコードとして作られるため、特別な処理はいらない見込み（確認する） |
| 6 | CRM のユーザー設定のタイムゾーンと PC のタイムゾーンが違う場合 | 初版は PC のタイムゾーンで表示する（どちらも JST の前提）。サーバーのタイムゾーンは設定で選ぶ（5.3） |
| 7 | 接続先の CRM の URL と、社外から使うときの経路（VPN など） | 利用者に確認する |
| 8 | 配布方法（自分だけで使うか、社内に配布するか） | 初版は自分用。配布する場合はコード署名を検討する |
