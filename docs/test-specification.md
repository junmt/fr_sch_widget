## 1. 方針

### 1.1 テストの種類

| 種類 | 対象 | 実行方法 | 自動化 |
|---|---|---|---|
| ユニットテスト（Rust） | `src-tauri/src` の判定・変換・通信のロジック | `cargo test --lib`（Windows 上） | ○ |
| ユニットテスト（TypeScript） | `src/logic.ts`, `src/settings-logic.ts` の表示ロジック | `npm test`（vitest） | ○ |
| 結合テスト（手動） | ウィンドウ・トレイ・通知・自動起動など、OS と画面を伴う部分 | 7章の手順で確認 | × |

### 1.2 デシジョン表の読み方

- **条件**の行の `Y` / `N` は、その条件を満たす / 満たさないことを表す。`-` はどちらでもよい（結果に影響しない）ことを表す。
- **動作**の行の `○` は、その動作が起きることを表す。
- 各ルール（列）に **テストID** を振る。テストコードの関数名の先頭にも同じ ID を付ける（例：`pr01_...`、`it("PH-03 ...")`）。
- 条件の組み合わせのうち、起こりえないものは「不可能」として理由を書く。
- 「-」でまとめたルールは、まとめた組み合わせのすべてをテストで確認する（「全組み合わせ」と書いた表）。

### 1.3 網羅の考え方

各関数について、次の観点をすべて検討した。該当しない観点は「N/A」と理由を書いた。

1. 正常系（代表的な入力）
2. 境界値（空、0、最小 / 最大、ちょうど、±1）
3. 異常系（不正な形式、null、通信の失敗）
4. 副作用（状態の変化、外部への呼び出しの回数と引数）
5. 冪等性（同じ入力を2回与えたとき）

### 1.4 テストの前提

- 時刻を扱うテストでは、タイムゾーンを JST（UTC+9）に固定した `FixedOffset` を使う（PC の設定に左右されないようにする）。
- 通信のテストでは、`mockito` のモックサーバーで CRM の `webservice.php` の応答を再現する。実際の CRM には接続しない。
- 資格情報マネージャー（`keyring`）は OS の機能なので、ユニットテストでは呼ばない（結合テストで確認する）。
